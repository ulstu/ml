# Эксперимент: когда LLM дает преимущество в MAS склада

## Гипотеза

LLM не должна улучшать маленькую транспортную задачу сама по себе. На малом складе классические модели — Contract Net, congestion game, A* и локальные traffic rules — быстрее и стабильнее.

Ожидаемая полезная конфигурация для LLM:

- большой склад, где разница между коротким центром и обходом уже заметна;
- несколько роботов и много открытых задач одновременно;
- есть альтернативные маршруты: северный, южный, восточный и западный обходы;
- центральный коридор считается потенциально перегруженным инспекционным трафиком, но не закрывается жестко;
- LLM используется только на стратегическом уровне: меняет веса и задает шлюз `go_agents`/`hold_agents`, но не управляет движением роботов напрямую.

Именно такую конфигурацию добавляет сценарий `large_maintenance_9_tasks_8_robots`.

## Что изменилось

Webots-сцена увеличена по горизонтальным координатам в `3.4` раза. Площадь пола стала больше в `3.4 * 3.4 = 11.56` раза. Роботы и грузы не масштабируются как объекты, поэтому на большой сцене они остаются визуально читаемыми.

Общие координаты вынесены в:

```text
controllers/warehouse_supervisor/warehouse_geometry.py
```

Этот модуль синхронизирует Webots-сцену, `scenario.py`, `planner.py`, `dry_run.py` и эксперимент.

## Методика

Скрипт:

```text
controllers/warehouse_supervisor/llm_value_experiment.py
```

Команда фактического прогона:

```bash
PYTHONPYCACHEPREFIX=/private/tmp/codex_pycache \
MAS_VECTOR_DEBUG=0 \
OLLAMA_MODEL=qwen2.5:0.5b \
/Users/hiber/miniforge3/bin/python3 \
  ml_course_ru/semester_2/lecture_04_multiagent_systems/webots_game_theory_warehouse/controllers/warehouse_supervisor/llm_value_experiment.py \
  --timeout 18 --dt 1.5
```

Для каждого сценария выполняются два режима:

- `fallback`: детерминированная стратегия без LLM.
- `llm`: RAG + SQLite vector DB + Ollama `qwen2.5:0.5b` + guardrails.

Guardrails нужны не для ручного управления роботами, а для безопасной формализации LLM-ответа: центральные ребра основной сцены не закрываются полностью, `safety_margin` ограничен, численные веса проверены, а число одновременно активных рейсов ограничено вместимостью семейств зон `A/B/C`. После этого те же Contract Net и congestion game выбирают назначения и маршруты.

Экспериментальный цикл быстрый стратегический: он использует те же `Task`, `Route`, `Strategy`, Contract Net и congestion game, но не запускает дорогой A* на каждом малом шаге. Полный операционный A* остается в Webots и `dry_run.py`.

## Где LLM выиграла

Выигрыш получился в `large_maintenance_9_tasks_8_robots`.

Сравнение:

- `Makespan`: `294.0 -> 252.0`, улучшение на `42.0` секунды.
- `Wait`: `472.5 -> 28.5`, снижение ожидания на `444.0` секунды.
- `Bypass`: `3 -> 6`, то есть LLM-стратегия действительно увела больше потока с центра.
- `Distance`: `545.6 -> 578.2`, путь стал длиннее, но система выиграла за счет меньших задержек.

Это тот случай, где LLM полезна: она не строит траекторию, а помогает выбрать стратегическую политику, когда текстовое правило говорит, что центр частично занят. Эти численные значения относятся к headless-эксперименту `llm_value_experiment.py`; текущая Webots-сцена дополнительно проверяет наглядность маршрутов и локальное выполнение контроллерами роботов.

## Что выдала Ollama

Для текущей Webots-сцены LLM возвращает стратегию без жесткого закрытия центра. Пример фактического ответа после guardrails:

```json
{
  "battery_weight": 2.0,
  "blocked_edges": [],
  "congestion_weight": 3.8,
  "deadline_weight": 0.3,
  "go_agents": ["R4", "R5", "R6"],
  "hold_agents": ["R0", "R1", "R2", "R3", "R7"],
  "max_active_tasks": 3,
  "max_new_assignments": 3,
  "safety_margin": 0.72,
  "traffic_rule": "center conflicts expected",
  "travel_weight": 0.3
}
```

После guardrails стратегический слой поднимает `congestion_weight`, оставляет `blocked_edges=[]` для основной сцены и ограничивает активные рейсы тремя семействами зон `A/B/C`. Дальше маршруты выбирает congestion game, а не LLM.

## Проверка Webots-сцены

После синхронизации визуальной разметки и маршрутов batch-запуск Webots завершился успешно:

```text
[success] completed=A,B,C,A2,B2,C2,A3,B3,C3 time=391.9
```

В этом прогоне центральные маршруты реально используются (`B_center`, `C_center`, `A_center_2`, `B_center_2`, `A_center_3`), а ожидание свободных роботов объясняется не пустой дорогой, а вместимостью зон: одновременно активны не более трех семейств доставок `A/B/C`.

## Интерпретация

LLM не дает универсального выигрыша.

На `large_standard_3_tasks_4_robots` она ухудшила результат: слишком рано выбрала обходы, хотя конфликтов почти нет. На `huge_redundant_12_tasks_10_robots` она тоже не помогла: дополнительных обходов стало больше, но ожидание выросло.

Польза появляется при сочетании трех факторов:

- есть текстовое или контекстное правило, которого нет в простом fallback;
- есть альтернативные маршруты и центральные маршруты, совпадающие с визуальной разметкой;
- цена ожидания у конфликтного ребра или зоны выше, чем цена лишнего расстояния.

## Практический вывод

Для этой MAS LLM целесообразна не как водитель роботов, а как стратегический интерпретатор правил склада. Ее стоит подключать при сценариях уровня:

- `8+` роботов;
- `9+` активных заявок, открытых одновременно;
- несколько конкурирующих обходных маршрутов;
- динамические правила: инспекция, приоритет клиента, временное повышение штрафа коридора или ограничение вместимости зоны.

Для маленькой базовой сцены лучше использовать только формальные модели без LLM.
